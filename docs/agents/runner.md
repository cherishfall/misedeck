# Mise runner

> [简体中文](../../zh-CN/docs/agents/runner.md)

The runner is the layer between the Tauri commands and the mise CLI. It lives in `misedeck/src-tauri/src/mise.rs` and is split into two parts:

- **Pure runner** — `run_mise(mise_path, req, on_event)` builds argv, spawns mise, captures stdout/stderr in background reader threads, and invokes `on_event` for every line plus a final `Exit`. `run_mise_tracked` is the same run with a `run_id`, which is what makes it cancellable (see Process tree). The function has no Tauri imports so it is unit-testable against a fixture binary.
- **Tauri command** — `run_mise_command(cwd, args, runId, on_event)` validates input, resolves the mise binary (cached on first call), and pipes the runner's events into a `tauri::ipc::Channel<RunEvent>`. `runId` is the panel's id for the run; `cancel_run(runId)` uses it. The final `RunCommandResult` enum is returned as a structured value (never throws on the JS side). This command is also the success/failure boundary (issue #221): a non-zero exit comes back as the error variant with mise's stderr attached, while `run_mise` itself still reports the raw `RunOutcome`.

## Argv shape

`run_mise_command` always passes literal argv — no shell, no interpolation. The `-C <dir>` flag is prepended when `cwd` is `Some`, followed by the user-supplied args. `validate_run_args` (mise.rs) enforces two rules, both narrowed from the original #18 guardrail by #160: args must be non-empty, and a token *starting with* `-` (a flag/option) must not contain a shell metacharacter (`;`, `|`, `&`, `` ` ``, `$`, `\n`, `\r`). Everything else — the subcommand, positionals, `run` values, `set` values — is inert data in a shell-less spawn and passes through untouched, so values like `npm run build && npm run test` or a `DATABASE_URL` containing `&` remain saveable from the GUI. Shell injection is impossible by construction (no shell ever sees the argv), not by rejecting values.

## Streaming

The runner uses background reader threads (one per pipe) to split lines and forward them through a bounded `mpsc::sync_channel` (256 lines; a child that outruns the poll loop applies backpressure instead of growing the queue). The main loop non-blocking-drains the channel between `try_wait` polls so the panel sees output in real time. The runner auto-kills the process at `STREAMING_TIMEOUT` (30 minutes, per the conventions); the install script has the same ceiling at 5 minutes, and read-only queries at 2 minutes. That read ceiling is not limited to the captured path: a read dispatched through the panel (`readOnly` → `run_mise_tracked_read_only`) takes its deadline from the same read ceiling — the tables load it on their own and offer no cancel, so a hung mise must be reaped in minutes, not half an hour (issue #283). Mutations and `mise run` keep the 30-minute ceiling.

Memory is capped by construction (issue #277). A single line retains at most 8 KiB; bytes past the per-line cap are dropped but still consumed from the pipe, so a newline-free writer cannot stall the child or grow the reader's buffer. Each stream retains at most 2 MiB in total — the same `CappedStream` feeds both the streamed transcript and `RunOutcome.stdout` / `stderr` — and lines beyond the aggregate cap are dropped while the readers keep draining, so a chatty long-running task cannot exhaust memory. When a cap first withholds output on a stream, the runner emits a typed `RunEvent::OutputTruncated { stream }` (at most once per stream), which the panel renders through i18n. It is a channel event, never a marker line inside stdout: the captured output stays byte-faithful and UI copy stays localized. Streaming is one loop, not two: `drive_child` (below) drives both the mise runner and the installer.

Readers read bytes and decode each line with `String::from_utf8_lossy`, so one invalid byte can never end a reader, truncate the transcript, or close the pipe under a still-running child (issue #222; `RunOutcome` already promises lossy decoding). Once the child is gone the runner drains both channels until the readers close them, bounded by `READER_SHUTDOWN_BOUND` (1 second): draining first frees capacity for a reader blocked in `send`, so the tail is not lost when the queue was full. A grandchild that inherited the pipe (`npm run dev &`, a daemon) can keep it open forever and must not be able to swallow the exit event at the bound; a reader still blocked then is abandoned — its handle is dropped and the thread exits on its own when the pipe finally closes (#277).

The loop itself is shared (issue #282). `drive_child` in `mise.rs` is the single implementation of spawn → poll → cancel → deadline → exit → reader shutdown; `PipeMode` decides whether a pipe is split into transcript lines (`Lines`) or read as one raw payload (`Raw`, see Captured mode). `run_mise_timed` and `run_install_command` are thin wrappers that only map the loop's `DriveOutcome` to their own result type and error wording. The loop used to be copied in both files (~90 lines), so a fix on one side could silently miss the other; every exit path now emits exactly one `RunEvent::Exit` from one place.

## Process tree

Timeouts, cancel and app quit terminate the **whole process tree**, not only the direct child (issue #223). `process_tree.rs` is the single home for this: both runners (`mise.rs`, `install.rs`) spawn through it.

- **Spawn**: every child is put in its own process group — unix `pre_exec` + `setsid()`, Windows `CREATE_NEW_PROCESS_GROUP`.
- **Kill**: unix `killpg(pgid, SIGKILL)`; Windows `taskkill /F /T /PID`. `child.kill()` stays as a fallback for the direct child when the group signal cannot work (the process left its group, `taskkill` is missing, a platform with neither mechanism). This is what makes `sh -c "curl … | sh"` stop: killing `sh` alone left `curl` and the installer writing shims, and `mise run` left the task shell running.
- **Cancel** is still a *soft* cancel in the panel: the run is marked cancelled immediately and the button is released, without waiting for the process. What changed in #223 is that the cancel now reaches Rust — `cancel_run(runId)` — and the runner that owns the child tears the group down within one poll slice (≤ 50 ms). The kill always runs on the thread that owns the `Child` handle, never from the cancel call, so a cancel can never signal a pid the app did not start.
- **Quit**: Tauri's `RunEvent::ExitRequested` and `RunEvent::Exit` kill every group still in the process-wide registry, so closing the window during an install does not leave downloads running. The sweep runs twice, with a short bounded delay between (issue #289): a child is registered only after `Command::spawn` returns, so a quit landing in between would snapshot a registry that does not contain it. The second sweep collects that child; the delay is synchronous because `Exit` fires immediately before the process ends and a detached timer would not be guaranteed to run.
- **Pid reuse**: the registry holds only children this process spawned and has not reaped. An entry is removed in the same step that reaps it — a reaped pid is free for reuse — and `try_wait` holds the registry lock across both, so a live entry always names a pid this app still owns. `terminate_all` snapshots the group ids under that lock and kills only after releasing it (issue #284): the Windows kill waits for `taskkill`, which walks the subtree and can take seconds per tree, and holding the lock across that wait stalled every runner thread's `try_wait` poll for the whole sweep, turning window close into an app-wide freeze.

Platform note: Windows is covered at runtime by the `windows-latest` CI job, which runs the full suite (`cargo test --all-targets --features fixtures --no-fail-fast`). Four behavioural tests drive the real `taskkill /F /T` path there: cancel and timeout killing a grandchild (`tests/runner.rs`; cross-platform since the fixtures became Rust binaries), and the app-exit sweep `terminate_all` plus `terminate_tree` (unit tests in `process_tree.rs`, which can reach the crate-private sweep) — the last two with a PowerShell child that starts a hidden `ping` grandchild, asserting through `tasklist` that both processes are gone (#278, #284). Unix runs the same `terminate_all` test with `sh` + `sleep`.

## Captured mode

Captured reads — `run_mise_json` and the read helpers behind it (`mise ls`, `env`, `config ls`, `tasks`, `plugins`, `outdated`, `doctor`, `registry`, `trust --show`, the `detect_mise` version probe) — go through `run_mise_capture`: the child is driven by the same `drive_child` loop as the panel, but both pipes are read in **raw mode**. stdout is taken as bytes to EOF, never split on `\n` and never capped per line, so the aggregate `MAX_STREAM_BYTES` (2 MiB) is the only bound. This is a correctness requirement, not a size preference: real mise emits `ls-remote --json <tool>` as one compact line (51,741 bytes for node on 2026.10.17, 74,716 for python), and the transcript's 8 KiB per-line cap cut it into an unparsable prefix — `PARSE_FAILED` for every real tool (issue #282). A payload that does exceed 2 MiB is an explicit `PARSE_FAILED`, never a silent prefix. The streaming panel path keeps its line caps unchanged.

Error mapping is the same for both modes: non-zero exit + non-empty stderr → `COMMAND_FAILED`, malformed JSON → `PARSE_FAILED`, timeout → `TIMEOUT`.

The one read with a second attempt is `mise registry`, whose table fallback exists for a mise that has no `--json`. It retries only on a usage error (exit 2) or unparseable JSON; a genuine failure is returned with its own stderr and exit code instead of paying a second read ceiling and replacing the original error (issue #289).

## Testing

Tests live in `misedeck/src-tauri/tests/`. The fixture-mise script (`tests/fixtures/mise/fixture-mise`) is the only thing the runner ever calls; the user's real mise binary is **never** touched. New fixture slugs follow the conventions.md layout (`tests/fixtures/mise/<argv-joined-by->`); the existing set lives in that directory. The `serial_test` crate serializes tests that share the `FIXTURE_MISE_SLUG` env var.

## Frontend hook

`useExecution()` (in `misedeck/src/components/ExecutionPanel/useExecution.ts`) is a small reducer + Tauri `Channel` consumer. Pages call `run({ cwd, args })`; the panel reflects state, lines, and exit. Every foreground run carries its id as `runId` on the invoke, and `cancel()` marks the entry cancelled then fires `cancel_run` with that id — fire-and-forget, because the panel must never wait for a process to die (issue #223). The `ExecutionPanel` component renders the docked deck per `docs/design/visual-language.md`.
