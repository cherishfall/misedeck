# Internationalization (i18n)

> [简体中文](../../zh-CN/docs/agents/i18n.md)

How MiseDeck ships English and Simplified Chinese side by side, and how to
add a new string without breaking that promise.

> The no-concatenation engineering rule and its `lint:i18n-concat` guard live
> in [`conventions.md` → i18n](conventions.md#i18n) — one rule, one home.

## Stack (prescribed)

- **`react-i18next`** initialized in `src/i18n/index.ts`.
- Resource files at `src/i18n/en.json` and `src/i18n/zh-CN.json`.
- A typed catalog of every key the app uses at `src/i18n/keys.ts`.
- A language provider at `src/i18n/useLanguage.tsx` that exposes
  `language` and `setLanguage`, persists the choice in
  `localStorage("misedeck.language")`, and re-renders consumers on change.
- A reusable switcher at `src/components/LanguageSwitcher/`.

## Naming convention — flat IDs grouped by area

Keys are dotted paths, grouped by feature area. The top-level segment
mirrors a folder in the app (or a logical group if no folder yet). Use
the existing groups before inventing a new one — the canonical,
always-current list of groups is `src/i18n/keys.ts` (today: `common`,
`directory`, `sidebar`, `miseManagement`, `execution`, `failureNotice`,
`tooltip`, `activation`, `nav`, `home`, `trust`, one per page — `tools`,
`preview`, `env`, `tasks`, `settings`, `doctor`, `plugins` — plus
`states`, `labels`, `errorBoundary`, `errors`, `languages`, `theme`,
`about`).

Conventions:

- **Lower camelCase** within a segment (`commandFailed`, not `command_failed`).
- **Verbs first, nouns second** in `common.*` (e.g. `search` before
  `results`); nouns first elsewhere.
- **No positional or page-specific prefixes** — group by area, not by
  page, so a label that moves between pages keeps its key.

## How to add a new string

Three steps, all in the same commit:

1. **Add the constant** to `src/i18n/keys.ts` in the right group
   (e.g. `common.retry: "common.retry"`).
2. **Add the same path** to **both** `src/i18n/en.json` and
   `src/i18n/zh-CN.json`. Same path, same nesting, same indentation.
   The English copy is the source of truth for tone; the Chinese copy
   may be a faithful translation or a localized rewrite, but never an
   empty string.
3. **Use the constant** at the call site:
   ```tsx
   <button>{t(I18N_KEYS.common.retry)}</button>
   ```
   Always go through `I18N_KEYS` — never type a string literal — so
   the compiler catches typos in the catalog.

Then run the guard:

```bash
npm run lint:i18n
```

It must exit zero. If it doesn't, the two resource files are out of
sync (see "Why every key MUST be in both files" below).

## Why every key MUST be in both files (in the same commit)

A key present in `en.json` but missing from `zh-CN.json` means the
Chinese UI would silently fall back to the English copy. Worse, a
key in `zh-CN.json` but missing from `en.json` means the English
fallback itself is missing, so the user sees a raw dotted path. Both
are bugs we want to catch at build time, not at the user's eye.

`scripts/check-i18n.ts` walks both JSON trees, computes the leaf-key
set for each, and exits non-zero with a clear diff if they differ.
The script is wired into `npm run lint:i18n` and the `npm run ci`
aggregate. **CI red means a key landed in only one file.** The fix is
to add the missing translation (or remove the unused key), not to
disable the check.

## How the language is chosen

The detection chain, in order of precedence:

1. **`localStorage("misedeck.language")`** — set by
   `<LanguageSwitcher>` when the user picks a language explicitly.
   Survives a relaunch; overrides everything below.
2. **Browser language** (`navigator.language`) — the OS preference,
   resolved by `i18next-browser-languagedetector` on first run. A
   Chinese-locale browser starts in `zh-CN`; everything else starts
   in `en`.
3. **Fallback** — `fallbackLng: "en"` in `src/i18n/index.ts`. If
   nothing above matches, the UI is English.

The provider re-renders on every `languageChanged` event, so toggling
the switcher updates all visible copy without a page reload.

## Where the error codes live

`docs/agents/conventions.md` pins a fixed set of `AppError.code`
values:

```
MISE_NOT_FOUND  MISE_TOO_OLD  COMMAND_FAILED  PARSE_FAILED  TIMEOUT  TERMINAL_NOT_FOUND
```

Key-shaped `AppError.message` payloads resolve through the `errors.*`
group. The keys the Rust side can emit are:

- `errors.miseNotFound` (MISE_NOT_FOUND)
- `errors.miseTooOld` (MISE_TOO_OLD; carries `{{found}}` / `{{minimum}}`)
- `errors.terminalNotFound` (TERMINAL_NOT_FOUND)
- `errors.timeout` (TIMEOUT)
- `errors.captureCap` (PARSE_FAILED; carries `{{limit}}` — the capture cap
  in MiB, humanized on the Rust side so the reader never converts a byte
  count)
- `errors.parseFailed` (PARSE_FAILED; carries `{{cmd}}` / `{{shape}}` — the
  command that ran and the payload shape MiseDeck expected. Both sides
  emit it: the frontend's shape checks (`api/miseTools.ts`,
  `api/mise.ts`) and the Rust boundary (`src-tauri/src/mise.rs`). One
  message for the whole class, so a zh-CN UI never renders
  MiseDeck-authored English detail.)
- `errors.commandFailed` (COMMAND_FAILED; carries `{{cmd}}` / `{{code}}` —
  the command that ran and its exit status. The Rust boundary emits it
  for every non-zero exit: `mise trust --show`, `mise doctor`,
  `mise registry`, `mise plugins ls`, `mise tasks edit --path`,
  `mise self-update`, and the generic run boundary.)
- `errors.installFailed` (COMMAND_FAILED; carries `{{code}}` — the exit
  status of the official mise installer script.)
- `errors.spawnFailed` (COMMAND_FAILED; carries `{{task}}` / `{{reason}}` —
  the operation and the OS error. The OS text is data, not copy.)
- `errors.waitFailed` (COMMAND_FAILED; carries `{{task}}` / `{{reason}}` —
  the operation and the OS error.)
- `errors.backgroundTaskFailed` (COMMAND_FAILED; carries `{{task}}` — the
  operation whose background task died.)
- `errors.cancelled` (COMMAND_FAILED; carries `{{task}}` — the operation
  the user cancelled. This is also the runner's cancellation signature:
  `useExecution.ts` matches the exact message to settle a cancel-racing
  rejection as cancelled, not failed (issue #301).)
- `errors.emptyArg` (COMMAND_FAILED; carries `{{arg}}` — the argument that
  was empty.)
- `errors.invalidArg` (COMMAND_FAILED; carries `{{arg}}` / `{{value}}` —
  the argument that was rejected and the offending value.)
- `errors.notADirectory` (COMMAND_FAILED; carries `{{path}}` — the path
  that is not a directory.)
- `errors.readFailed` (COMMAND_FAILED; carries `{{path}}` / `{{reason}}` —
  the file and the OS error.)
- `errors.homeNotFound` (COMMAND_FAILED — the home directory could not be
  resolved.)
- `errors.unparsableOutput` (COMMAND_FAILED; carries `{{cmd}}` — the
  command whose output MiseDeck could not read. The raw output stays in
  the `stderr` field, verbatim.)
- `errors.terminalLaunchFailed` / `errors.terminalLaunchExited` /
  `errors.terminalLaunchTimeout` (COMMAND_FAILED; carry `{{platform}}` /
  `{{app}}` / `{{path}}` / `{{command}}`, plus `{{reason}}`, `{{code}}`
  or `{{seconds}}` — the terminal that was launched, the directory it
  was launched for, and the exact argv that was attempted.)
- `errors.linkRejected` (COMMAND_FAILED; carries `{{reason}}` — why the
  link was refused before it reached the browser.)
- `errors.browserRefused` (COMMAND_FAILED; carries `{{reason}}` — the
  opener's own error.)
- `errors.updateFeedInvalid` (COMMAND_FAILED; carries `{{reason}}` — why
  the release feed was not a release feed.)
- `errors.updateCurlFailed` (COMMAND_FAILED; carries `{{reason}}` — the
  OS error from curl.)
- `errors.updateFeedTooLarge` (COMMAND_FAILED; carries `{{limit}}` — the
  byte cap the feed exceeded.)
- `errors.updateRequestFailed` (COMMAND_FAILED — the release feed request
  did not succeed.)
- `errors.shellRcUnreadable` (COMMAND_FAILED; carries `{{reason}}` — the
  OS error from reading the shell's rc file.)
- `errors.windowChromeFailed` (COMMAND_FAILED; carries `{{reason}}` — the
  OS error from theming the window.)

The frontend emits two keys of its own — `errors.ipcFailed` (COMMAND_FAILED;
carries `{{detail}}` — the runtime's own rejection text) and
`errors.unexpectedIpcResponse` (COMMAND_FAILED — the IPC boundary
answered with something that is not a run result). In both, MiseDeck's
words are the catalog's sentence and the runtime's text is the data it
carries.

The `shape` parameter of `errors.parseFailed` is a locale-neutral token,
not prose: it names one of the `errors.shape.*` leaves of the catalog
(`array`, `configFilesResult`, `documented`, `objectBySetting`,
`objectByTool`, `objectByVariable`, `report`, `rowsWithPath`,
`validJson`, `versionDate`, `versionString`), and the catalog holds that
token's phrase in both locales. `resolveAppErrorMessage` looks the
phrase up before the message is translated, so the Rust side emits the
token without knowing the reader's language. Adding a shape means adding
the token to the catalog in both locales — and, when the Rust side emits
it, to the `parse_shape` module in `src-tauri/src/mise.rs`. `documented`
is the resolver's fallback for a parse failure that names no shape at
all: the sentence stays whole and still names the command.

The command-failure class uses the same contract for the parameters
that name a *kind* rather than data. `{{task}}` names one of the
`errors.task.*` leaves (`cwd`, `install`, `mise`, `other`,
`selfUpdate`, `trust`), `{{arg}}` one of the `errors.arg.*` leaves
(`command`, `cwd`, `flag`, `other`, `task`, `theme`, `tool`),
`{{reason}}` one of the `errors.linkReason.*` leaves (`credentials`,
`empty`, `host`, `other`, `scheme`, `tooLong`, `whitespace`) or the
`errors.feedReason.*` leaves (`noEntry`, `notAtom`, `other`). Each
group's `other` leaf is the resolver's fallback for a failure that names
no kind at all. The Rust side emits the same tokens — the `token` module
in `src-tauri/src/mise.rs` — and the frontend mirrors them in
`MESSAGE_TOKEN` (`misedeck/src/utils/appError.ts`).

A parameter value that carries the `|` delimiter is percent-encoded
(`|` → `%7C`, `%` → `%25`) on the way onto the wire, so a path, an argv,
or a runtime message can never split the message into bogus parameters.
The frontend decodes it in `parseAppErrorMessage`.

`errors.unknown` is the resolver's fallback for a key-shaped message the
catalog does not know — a raw key never renders.

Every UI site that displays `err.message` resolves it through
`resolveAppErrorMessage` (`misedeck/src/utils/appError.ts`), which parses
the `key|param=value|…` wire format and passes raw text through verbatim
for a message that is not key-shaped. A parse failure is key-shaped
(issue #310) and so is a command failure (issue #311), so both resolve
like every other message; a detail that predates the key still renders
its raw text verbatim. Codes with dedicated page state views keep those
views: the HomePage too-old gate renders `states.tooOld.*` and only
parses the params out of `message` (via the shared
`parseAppErrorMessage`).

**mise's own stderr is never keyed.** It is the CLI's output — data, not
copy — and it stays verbatim in the `stderr` field of the error (or, when
the error has no other field for it, as a parameter the catalog does not
translate). Only MiseDeck's own words are keyed.

The resolver references these keys in its `KNOWN_MESSAGE_KEYS` set
precisely because dynamic resolution is invisible to static `t()`
call-site scans — do not delete them as "dead keys".

The UI pattern-matches on the `code` (see `conventions.md`) for the
human copy.
Inventing a new error code is a deliberate API change — open an
issue, update this doc, add the key to both resource files, and
extend `misedeck/src/types/tauri.ts` and
`misedeck/src-tauri/src/mise.rs` in the same change.

## Adding a new language

`SUPPORTED_LANGUAGES` in `src/i18n/useLanguage.tsx` is a `const`
tuple — to add a third language:

1. Append the BCP-47 code (e.g. `"ja"`) to the tuple and to
   `supportedLngs` in `src/i18n/index.ts`.
2. Drop a new `src/i18n/<code>.json` next to the existing pair.
3. Update `I18N_KEYS.languages` with the display label and add the
   option to `LANGUAGE_LABELS` in `useLanguage.tsx`.
4. Translate every existing key into the new file (the `lint:i18n`
   script will refuse to pass until parity is achieved).
