# 1.0.0 frontend audit（static）

> Scope: `misedeck/src/**` — 106 files, ~17,876 lines TS/TSX plus 40 CSS modules (5,075 lines),
> `index.html`, `tokens.css`, `fonts.css`, `src/assets/fonts/`.
> Baseline: `master @ 37d27fb` (1.0.0-beta.17), clean tree.
> Method: **static only** — no app launch, no screenshots, no dev server, no build. Read-only repo
> linters were run (`npx tsx scripts/check-*.ts`), plus `npx tsc --noEmit` and
> `npx tsx --test "src/**/*.test.ts"`.
> Rules audited against: `AGENTS.md`, `CONTEXT.md`, `docs/agents/conventions.md`,
> `docs/design/ui-ux-rules.md`, `docs/design/visual-language.md`,
> `docs/design/product-logic.md`, ADR-0004/0005/0007/0008/0009.
> This is an audit record; exempt from zh-CN mirroring.

## Verdict summary

- **P0 = 0.** Nothing structurally blocks a 1.0.0 build: the app boots, every route resolves
  except unknown paths, all twelve lint guards pass, `tsc` is clean, 133/133 unit tests pass.
- **P1 = 2.** Both are layout/hit-area defects a first-time user sees in the first session at the
  **default** window size — not edge cases:
  1. the two widest data tables (Tools, Env) exceed the available content width at 1200×720, so the
     primary page opens with a horizontal scrollbar and its trailing action column clipped;
  2. the shared floating layer never clamps vertically, so a version-switch menu opened from a lower
     table row extends past the bottom of the window and keyboard focus can land on an item that is
     not on screen.
- **P2 = 18.** Concentrated in four groups: **silent `invoke` failures** (the known #249 hole plus
  three more sites), **custom-widget ARIA/keyboard gaps**, **dead code / template residue**, and
  **font licensing + one glyph coverage hole**.
- The engineering discipline is unusually high for a pre-1.0 GUI: zero `any`, zero non-null
  assertions, zero `console.*`/`TODO`, every read query has a rendered error state, all 442 i18n
  keys are live, and every persisted value has a versioned key. The debt is not correctness — it is
  a handful of surfaces that were never reached by the chrome that was designed for them.

## P1 — first-time user hits it in the first session

### P1-1 The Tools and Env tables demand horizontal scrolling at the default window size

- **Evidence.**
  - Default window is **1200×720** (`src-tauri/tauri.conf.json:18-21`), sidebar
    `--layout-nav-width: 196px` (`tokens.css:142`), page padding `var(--space-6)` = 26px per side
    (`PageShell.module.css:204`, `tokens.css:127`). Available content width at the default size:
    `1200 − 196 − 52 = **952px**`.
  - Tools table declares `min-width: 976px` (`ToolsPage.module.css:59`), the sum of
    `150 + 220 + 130 + 120 + 216 + 140` (`ToolsPage.tsx:470-585`).
  - Env table declares `min-width: 980px` (`EnvPage.module.css:114`), the sum of
    `220 + 320 + 220 + 220` (`EnvPage.tsx:228-272`).
  - Both are unconditional, even though the Backend column is conditional
    (`ToolsPage.tsx:464, 545`) — without a `backend:name` row the rendered columns total 856px but
    the floor stays 976px.
  - `docs/design/ui-ux-rules.md:55` — "a data table never demands horizontal scrolling to read
    ordinary columns at **normal window widths**; below the table's declared `min-width` the table's
    own scroller scrolls horizontally".
- **Consequence.** Launch the app (1200×720), open **Tools**: the 976px `<table>` sits inside the
  952px `.scroller` (the `min-width` is applied to the inner `<table>`, `Table.tsx:159-229`, while
  the scroller is a plain `width: 100%` wrapper), so the scroller gains a horizontal scrollbar and
  the trailing **Actions** column — the only entry point to version management
  (`ToolsPage.tsx:565-586`) — starts 24px out of view. macOS uses overlay scrollbars that are
  invisible until scrolled, so the button simply looks cut off. **Env** is 28px over. The tables only
  fit below 1224px / 1228px of window width, and the two pages fit only if the user collapses the
  sidebar (56px → 1092px available). The #225 widening (Source 160 → 216, Env Value 320) is what
  pushed both over the line — 920 and 900 fit at 952.
- **Fix.** Trim ~56px from one column on each page (Tools: Source 216 → 192 still keeps
  `SOURCE_CELL_CHARS` ≥ 23, or Requested 130 → 110; Env: Source 220 → 190) so both floors land
  ≤ 940, and make the Tools floor track whether the Backend column renders. Either is a one-line
  change; re-run `check-css-tokens.ts` if `SOURCE_CELL_CHARS` moves.

### P1-2 FloatingMenu never clamps or flips vertically — menus open past the window edge

- **Evidence.**
  - `FloatingMenu.tsx:112-125` (`computePosition`) computes `top` but clamps **only** the horizontal
    axis: `left = Math.max(4, Math.min(left, maxLeft))`, while `top` goes in raw
    (`placement === "up" ? t.top - m.height - gap : t.bottom + gap`).
  - The layer is `position: fixed` inside a body portal with `overflow: hidden`
    (`FloatingMenu.module.css:12-22`), so nothing outside the viewport is reachable and no internal
    scrollbar is rendered at the layer level.
  - The consumer that hits it is the per-row version switch: `placement="down"`
    (`ToolsPage.tsx:910-913`), with a menu of one item per installed version capped at
    `max-height: 280px` (`ToolsPage.module.css:179-185`).
  - The shared `Tooltip` already implements the missing flip (`Tooltip.tsx:131-138`), so the
    primitive pair is inconsistent.
- **Consequence.** On the Tools page, click the version cell of any row whose top is below ~430px
  (the 4th row onward at 720px height, and every row in a long list): the menu's lower half is
  painted outside the window. Because the layer is fixed and the trigger is already near the bottom
  of the page, the items cannot be brought into view without first scrolling the page so the trigger
  moves up. Keyboard use is worse: focus enters the first item (`FloatingMenu.tsx:177-189`) and
  ArrowDown walks into items that are outside the viewport, so the focus ring disappears (WCAG 2.4.7
  / 2.4.11) while the menu still receives keys. The same math applies to the directory-recents menu
  and the app-version popover, but their anchors are near the top of the window, so the version cell
  is the reproducible case.
- **Fix.** Clamp and flip in `computePosition`:
  `if (top + m.height > innerHeight - 4) top = placement === "down" ? t.top - m.height - gap : innerHeight - m.height - 4;`
  and `top = Math.max(4, top)`. Six lines, same shape as the existing horizontal clamp; the
  `.useMenu` inner scroller then has a reachable scrollbar.

### P2-1 A rejected `detect_mise` leaves the Home page spinning forever

- **Evidence.** `HomePage.tsx:53-56` maps `undefined` to `{ status: "loading" }`;
  `HomePage.tsx:191-198` renders the "Detecting mise…" panel for that status; `query.isError` is
  never read. `query` uses `retry: false` (`:103-108`), so the state is permanent.
- **Consequence.** If the command rejects (IPC/capability failure, a panic inside the blocking
  closure), the launch page shows "Detecting mise…" indefinitely with no error, no retry and no
  diagnostic — the toolbar Refresh re-runs the same failing call. Every other page survives the same
  event because a *second* query's error banner renders; Home has only the one query, so nothing
  else speaks.
- **Fix.** Add `if (query.isError) return { status: "commandFailed", err: { code: "COMMAND_FAILED",
  message: String(query.error), stderr: "" } }` before the `undefined` branch.

### P2-2 The shell-activation probe's error state has no consumer

- **Evidence.** `activationContext.tsx:208-216` builds `{ kind: "error", message }`;
  `ActivationBanner.tsx:78-82` returns `null` for it (deliberate, documented);
  `DoctorPage.tsx:140` maps any non-`ok` state to `null`, rendered as `—`.
- **Consequence.** If reading the rc file fails (permissions, an unparsable profile), the user is
  never told: no banner, and the Doctor row shows the same `—` as "not yet probed". The banner
  header comment (`ActivationBanner.tsx:13-19`) even claims the opposite ("the banner shows a soft,
  message-only variant so the user is never blind") — stale doc against the code at `:78-82`.
- **Fix.** Render `state.kind === "error"` in the Doctor activation row with the resolved message
  (the state already carries display copy), and correct the banner's header comment.

### P2-3 A trust-probe error is a dead end: writes are disabled with no way to retry

- **Evidence.** `TrustBanner.tsx:65-69` renders the error banner with a message and **no action
  button**. `useTrustGuard` blocks every mutation on `reason: "error"`
  (`trustContext.tsx:287-289`). The only trust invalidation in the tree is after a successful
  `mise trust` (`trustContext.tsx:245`); no page's `onRefresh` includes `["mise","trust",cwd]`
  (`ToolsPage.tsx:318-326`, `EnvPage.tsx:108-118`, `TasksPage.tsx:212`, `PluginsPage.tsx:125`,
  `SettingsPage.tsx:128`, `DirectoryPreview.tsx:165-169`).
- **Consequence.** If the probe fails, every Unuse/Uninstall/Use/Install/Upgrade and every env/task
  write silently refuses (the guard early-returns after focusing the banner) and the banner says
  "write actions are disabled" with no remediation. The toolbar Refresh — the app-wide recovery
  affordance — does not re-probe. Recovery requires changing the directory context or restarting.
- **Fix.** Give the error banner a Retry that invalidates `["mise","trust",cwd]`, and add that key to
  each page's `onRefresh`.

### P2-4 `ExternalLink` swallows the opener failure (#249)

- **Evidence.** `ExternalLink.tsx:44-51` — `openExternalUrl(...).catch(() => window.open(...))`;
  in the app shell `window.open` is the dead path the component exists to avoid
  (`externalLink.ts:1-14`). The comment names #249 as the missing notice.
- **Consequence.** ADR-0009's manual update flow terminates at the Release page's Download link
  (`AppVersion.tsx:146-149`). On a machine where the opener fails (no default browser, a blocked
  handler), clicking Download does nothing at all: the user is told a new version exists and every
  route to it is silent. Same for the mise-docs link on the Home/missing states.
- **Fix.** After the fallback also fails, surface one inline sentence on the trigger
  ("Couldn't open your browser — the URL is: …") or copy the URL to the clipboard and say so. #249
  already tracks the global version of this; the Release link is the site that cannot wait.

### P2-5 The theme → native-chrome write is silent (#249)

- **Evidence.** `themeContext.tsx:68-71` — `void setWindowTheme(theme).catch(() => {})`.
- **Consequence.** The DOM theme flips (visible immediately), but the OS window chrome keeps the old
  theme with no indication. In practice the app can end up with a light body inside a dark title bar
  and stay that way for the session. Acceptable as best-effort, but it is the second half of #249 and
  should be listed there explicitly rather than only in a code comment.
- **Fix.** None required for 1.0.0 if #249 lands with a shared, throttled failure notice; otherwise
  at minimum log the failure into the execution panel's transcript, which already exists as a
  visible surface.

### P2-6 A failed cancel leaves the panel claiming the run stopped

- **Evidence.** `useExecution.ts:231-245`: the cancel handle dispatches `{type:"cancel"}` (panel shows
  "cancelled" immediately), then `void invoke("cancel_run", …).catch(() => {})`.
- **Consequence.** `cancel_run` is the only thing that tears down the process group (#223). If it
  fails or races, `curl | sh` or `mise install` keeps running while the panel says "cancelled" and
  the reducer ignores every later event for that run (`executionState.ts:129-151`, terminal status).
  The user believes a multi-minute install was stopped; it is still writing to `~/.local/share/mise`.
- **Fix.** Have `cancel_run` report failure and, on failure, move the run back to "running" (or add
  an intermediate `cancelling` status that survives until the exit event arrives). Cheap version:
  keep the optimistic flip but append a transcript line "the run did not stop".

### P2-7 Two unguarded `localStorage` calls at boot, above the error boundary

- **Evidence.** `themeContext.tsx:58` (`localStorage.getItem` in the `useState` initializer) and
  `:74` (`setItem` in `setTheme`), plus `useLanguage.tsx:62`. Every other persistence path uses
  `loadPersistent`/`savePersistent`, which are wrapped (`usePersistentState.ts:19-36`); the inline
  boot script in `index.html:24-31` wraps the *same* read in try/catch.
- **Consequence.** A denied/blocked storage origin makes `ThemeProvider` throw during render. It sits
  **above** `RoutedErrorBoundary` (`main.tsx:53-64`), so there is no fallback: the window renders
  nothing, permanently. `setTheme` instead throws inside the click handler, so the toggle silently
  does nothing while the DOM theme may already have changed.
- **Fix.** Route both through `loadPersistent`/`savePersistent` (already exported from
  `hooks/usePersistentState.ts`). This also collapses the duplicated key literal.

### P2-8 No catch-all route

- **Evidence.** `main.tsx:65-80` — nine explicit routes, no `path="*"`. React Router renders `null`
  for an unmatched location.
- **Consequence.** Any unknown path renders an empty window: no sidebar, no nav, no way back. In a
  Tauri shell that needs a restart (or a manual reload to `/`). Reachable through a stray
  `window.open`, a future link typo, or a webview reload at a deep path.
- **Fix.** `<Route path="*" element={<Navigate to="/" replace />} />` — one line, and the
  ErrorBoundary's `resetKey` pattern shows the intent already exists.

### P2-9 The execution-panel run switcher is a `tablist` that does not follow the tabs pattern

- **Evidence.** `ExecutionPanel.tsx:171-222`: `role="tablist"` containing the count `<span>` (fine),
  the `role="tab"` chips, a focusable ✕ `IconButton` per finished run, and a "Clear" `<button>`.
  No `aria-controls`, no `role="tabpanel"` on the transcript, no `tabIndex` roving, no
  ArrowLeft/Right handler; every chip is a separate tab stop.
- **Consequence.** A screen reader announces a tab list with as many tabs as there are chips plus two
  stray controls, then "tab 1 of 4" moves focus one chip at a time. The visible behaviour (click a
  chip to switch transcripts) is already button semantics; the ARIA roles promise a keyboard model
  the widget does not implement. `lint:nested-interactive` passes because the close buttons are
  siblings, not descendants.
- **Fix.** Either implement the pattern (roving `tabIndex`, Left/Right/Home/End, `aria-controls` →
  `role="tabpanel"` on the transcript) or drop to `role="group"` +
  `aria-pressed` on the chips and move Clear/✕ outside the group. Grouping the chip and its ✕ in a
  wrapper with `role="presentation"` keeps the DOM as-is.

### P2-10 Focus indicators on hand-rolled inputs are a 1px border colour change

- **Evidence.** The global ring (`tokens.css:226-229`, `:focus-visible { outline: 1px solid var(--beam) }`)
  is suppressed rather than replaced in three places, all with `.input:focus { outline: none }`
  followed by **only** `border-color: var(--line-strong)`: `TableFilter.module.css:34-37`,
  `EnvPage.module.css:201-205`, `SettingsPage.module.css:174-177`. `Button` / `IconButton` /
  `NavItem` instead use the shared `--ring` (`Button.module.css:32-36`). The task editor is a
  weaker version of the same pattern — it also drops the ring, but its focus border is the accent
  (`TasksPage.module.css:240` + `:244`, `:267` + `:272`), which stays legible.
- **Consequence.** Keyboard focus on the table filter and on the env/settings add-forms is a
  `--line` → `--line-strong` transition with no accent — materially quieter than every other focus
  target in the app. `:focus` (0,2,0) beats the global `:focus-visible` (0,1,0), so the ring really
  is gone. In the Env add-form (name + value, two inputs) the user has to hunt for the focused
  field.
- **Fix.** Add `box-shadow: var(--ring)` to those `:focus` rules (or switch them to `:focus-visible`
  + `--ring`), matching `Button`.

### P2-11 An unanswerable directory probe is computed and dropped

- **Evidence.** `directoryAvailability.ts:13-15` defines `unknown` and promises "data honesty";
  `directoryContext.tsx:193` computes it but uses it only for the restore gate (`:221`). No component
  consumes `kind === "unknown"`.
- **Consequence.** When `directory_exists` fails, the app proceeds with a path that may not exist and
  every page renders its **own** mise failure with its own stderr block — precisely what
  `directoryAvailability.ts:5-7` says must never happen. The user sees N copies of a failure with no
  single explanation, and the directory context keeps showing a path that may be gone.
- **Fix.** Treat `unknown` like `unavailable` in the banner (different copy: "couldn't check this
  directory") and offer the same reselect action.

  `parseRegistryItem` (`:634`), `parseInstalledPlugin` (`:661`).

Type-only prop exports (`*Props`, `*Tone`, `HostPlatform`, …) were excluded — idiomatic.
`pruneRuns`' behaviour *is* covered, through the reducer
(`executionState.test.ts:52-72` exercises the cap from both sides), so it is only the `export`
keyword that is unused.

**Fix.** Drop the `export` keyword on the runtime ones.

### P2-13 Template residue still ships

- `src/assets/react.svg` (4.1 KB) — zero references anywhere in `src/` or `index.html`.
- `public/tauri.svg` (2.6 KB) — zero references.
- `public/vite.svg` — the **app favicon** (`index.html:4`), i.e. the shipped product still identifies
  itself with the Vite logo wherever the webview's icon is used (dev window, task switcher on
  platforms that read it).
- **Fix.** Delete both orphans, point the favicon at a MiseDeck mark (or remove the `<link>` and let
  the bundle icon win).

### P2-14 One hardcoded English string in a localized surface

- **Evidence.** `AddToolSection.tsx:540` — `` <Tooltip text={`latest → ${r.version}`}> ``. Every
  other tooltip in the tree goes through `t()` (the second literal, `DoctorPage.tsx:231`, is pure
  data). `latest` is mise's alias so the *token* is honest, but the surrounding string has no i18n
  key, so a zh-CN user sees English inside an otherwise translated table.
- **Fix.** Add `tools.addTool.latestAlias` = `latest → {{version}}` / `latest → {{version}}`（zh can
  say `最新版 → {{version}}`）and use `t(key, { version })`.

### P2-15 The upgrade arrow is not in any bundled font

- **Evidence.** `fonts.css:45` / `:65` declare `U+2191, U+2193` (↑ ↓) in the latin
  `unicode-range` but **not** `U+2192`. The app renders `→` as a data glyph in two places
  (`AddToolSection.tsx:543`, `DoctorPage.tsx:397`) via the shared `.upgrade-arrow` class.
- **Consequence.** The arrow is served by the next family in the stack (SF Mono / Menlo / a system
  serif), so in the same cell JetBrains Mono's `↑`/`↓` and a fallback `→` sit side by side with
  different weight and advance. Cosmetic, but it is exactly the class of drift #241 was opened to
  end.
- **Fix.** Re-subset the mono face with `U+2192` (Google's `latin` list omits it), or render the
  arrow as inline SVG like `LanguageSwitcher`/`AppVersion` already do.

### P2-16 The bundled OFL fonts ship without their licence text

- **Evidence.** `src/assets/fonts/README.md:31-40` states the three families are SIL OFL 1.1 and that
  "the OFL requires the copyright notice and licence to travel with the font files, so this file is
  part of that notice" — but the file contains neither the OFL text nor any copyright line, only
  links to the specimen pages. The fonts are embedded in every released binary (WebView assets).
- **Consequence.** A 1.0.0 binary redistributes three OFL works without the notice the licence
  requires. This is a release-compliance item rather than a UI defect, but it ships with the same
  artifact and is much cheaper to fix now than after the GA tag.
- **Fix.** Add `src/assets/fonts/OFL-CormorantGaramond.txt`, `…-SpaceGrotesk.txt`,
  `…-JetBrainsMono.txt` (full licence + the upstream copyright line) and include the directory in
  the bundle's resources (or an in-app "Licences" section reachable from the colophon, which also
  gives the external link a legitimate home).

### P2-17 A CJK path breaks the head-elision budget

- **Evidence.** `paths.ts:146-162` measures with `String.length` while the budget
  (`columnCharBudget`, `:108-112`) is expressed in mono *character advances*.
- **Consequence.** For a zh-CN user whose project folder is `项目/我的应用`, each CJK character takes
  two mono advances but counts as one in `shortenPathTail`, so the "basename stays visible" guarantee
  (#216) fails exactly on the paths where the tail is most needed — the CSS end-ellipsis then cuts
  the segment the function was preserving. MiseDeck ships a zh-CN UI, so this is not an exotic input.
- **Fix.** Weight the budget: `[...str].reduce((n, ch) => n + ((ch.codePointAt(0) ?? 0) > 0x2e80 ? 2 : 1), 0)`
  in the comparison loop.

### P2-18 Minor, cheap, or owner-decision items

- **Tooltip-per-cell tab stops.** `Tooltip.tsx:165` sets `tabIndex=0` on the wrapper when nothing
  inside is focusable — required by `ui-ux-rules.md` ("tooltips answer focus"). On the Tools and Env
  tables every data cell is wrapped (`ToolsPage.tsx:475, 540, 559`), so a 30-row table contributes
  90+ tab stops before the user reaches the Actions column. **Flagging for an owner decision**, not
  a defect: the rule is explicit and the alternative (focus-on-scroll, or a grid-style roving
  cursor) is a bigger design change than a 1.0.0 window.
- **The panel resize grip is pointer-only** (`ExecutionPanel.tsx:164-168`: `aria-hidden` div with
  `onPointerDown`, no `role="separator"`, no `tabIndex`, no arrow keys). Non-essential — the log
  scrolls — but it is a control with no keyboard path.
- **`DataRow` renders `dt`/`dd` outside a `dl` on Home** (`HomePage.tsx:253` inside `.rawWrap`).
  Invalid HTML; the label→value relation is lost to AT. Wrap in `<dl>` or give `DataRow` a plain
  rendering mode.
- **`clipboard.ts:33-46` steals focus.** The `execCommand` fallback focuses a hidden textarea, then
  removes it, so focus lands on `<body>` even when the copy succeeded. Rare (only when the Tauri
  plugin and the async API both fail), but it silently resets a keyboard user's position.
- **`useOwnRun` returns a fresh object each render** (`ExecutionContext.tsx:170`), so every consumer
  re-renders on any panel state change and `onLink`'s identity churns through `linkRun`
  (`ToolsPage.tsx:360`). Memoise the pair or return `[run, isRunning]`.
- **`pruneRuns` drops by start order, not finish order** (`executionState.ts:65-72`): a long run that
  finishes after three quick ones keeps its slot, and the three quick results are pruned first. Only
  affects which transcript survives; no data loss beyond the 3-run cap.
- **Dead tokens.** `--z-deck` (`tokens.css:159`) and `--layout-deck-collapsed-height` (`:144`) have
  zero references (the deck is `position: relative` in normal flow,
  `ExecutionPanel.module.css:1-14`); `--z-modal`'s comment still says "future modal layer" (`:161`)
  although `ConfirmDialog.module.css:8` uses it today. `check-css-tokens.ts` cannot catch these — it
  asserts referenced ⊆ defined (54 of 58), never the reverse. A one-line reverse check would make
  the token file self-pruning.
- **No ESLint at all.** `package.json` has no `eslint` dependency or config; `ci` is
  typecheck + node:test + the 12 bespoke linters. Nothing enforces rules-of-hooks or
  exhaustive-deps — e.g. `AddToolSection.tsx:172-180` intentionally omits `selectTool`, which is
  correct today and only a comment protects the next one. Adding
  `eslint@9` with only `react-hooks` would close the whole class for a few lines of config; flagged
  as an owner decision because it changes the toolchain.
- **`useOwnRun` early-return is silent by design** (`ExecutionContext.tsx:140-145`). Consistent with
  the documented convention; noted only because it is the one place a click can produce nothing.
