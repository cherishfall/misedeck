# 1.0.0 GA audit — features & mise CLI compatibility (2026-10-21)

> Scope: does the app implement the v1 checklist (ADR-0003) faithfully, and does every
> mise invocation it builds still exist and mean what the code assumes?
> Baseline: master `37d27fb` (`1.0.0-beta.17`), clean tree apart from this audit's files.
> Method: **static review + read-only CLI probes**. Nothing was launched, built or screenshotted;
> no mise config or repo file was modified. Local mise: `2026.10.15 macos-arm64 (2026-10-19)`;
> older-version behaviour was read from the tagged upstream sources (`v2025.1.0`, `v2025.12.5`).
> This is an audit record; exempt from zh-CN mirroring.

## Summary

- **P0 = 0** — nothing here blocks a 1.0.0 tag on its own.
- **P1 = 2** — both are user-visible on the Tools page, the app's main surface.
- **P2 = 7** — copy/metadata fidelity, one degraded Doctor path, one navigation drift.
- The debt clusters in three places: **①the outdated read asks mise for out-of-range
  upgrades and then offers an in-range upgrade button**, **②the declared mise floor
  (`2025.1.0`) predates `ls-remote --json` by eleven months**, **③the Plugins/Doctor reads
  throw away fields mise already returns**.

What is *not* broken is worth stating plainly: the whole argv surface exists, every parsed
JSON shape still matches, and the safety machinery (trust, `MISE_SAFE`, `-C` anchoring,
batch-operation bans) is intact. This is a compatible app with two wrong assumptions.

## Confirmed clean (checked, no action)

- **Route ↔ page inventory.** `main.tsx:60-90` declares 8 pages plus `/config → /preview`;
  that is exactly the page table in `docs/design/product-logic.md:57-64`. No phantom page,
  no unlisted page, every nav entry resolves.
- **Every subcommand and flag the app builds exists in mise 2026.10.15.** Probed one by one:
  `ls --json`, `ls --json <tool>`, `ls-remote --json <tool>`, `outdated --json [--bump]`,
  `registry --json`, `env --json`, `env --json-extended`, `set [-g] K=V`, `unset [-g] K`,
  `use [-g] tool@ver`, `unuse [-g] tool`, `install tool@ver`, `uninstall tool@ver`,
  `upgrade <tool>`, `link tool@ver path`, `tasks ls --json`, `run <name>`,
  `tasks add [--description] [--depends]… <name> -- <run…>`, `tasks edit --path <name>`,
  `config ls --json`, `settings ls --json-extended [--all] [--local]`,
  `settings set [--local] K V`, `settings unset [--local] K`, `plugins ls --urls`,
  `plugins install <name> <git-url>`, `plugins uninstall <name>`, `doctor --json`,
  `trust` / `trust --show`, `self-update --yes`, `version --json`. Zero renames, zero
  removals across the 2025.1.0 → 2026.10.x window (upstream release notes confirm no
  flag removals in the range; the 10.14–10.17 breaking changes are config/behaviour level).
- **JSON shapes still match the parsers.** `version --json` → `{version, latest, os, arch,
  build_time}` (Home reads `latest`, correct — see the note on release age below);
  `ls --json` keeps the snake_case set the app reads (`version`, `requested_version`,
  `install_path`, `symlinked_to`, `source{type,path}`, `installed`, `active`);
  `outdated --json` keeps `name/requested/current/bump/latest/source` (+`release_url`,
  unused); `env --json` is a flat map, `env --json-extended` is `{value, source, tool}`;
  `settings ls --json-extended` is `{value, type, description, source}`;
  `config ls --json` is `[{path, tools, override}]`; `registry --json` is
  `[{short, backends, bins, description, aliases}]`; `doctor --json` keeps every key the
  app touches. **No field the app reads has disappeared.**
- **Directory anchoring.** `resolve_cwd_anchor` (`mise.rs:347`) makes Global mode
  `-C $HOME` and Directory mode `-C <dir>`; `validated_cwd` (`lib.rs:506` and siblings)
  rejects empty/missing dirs before spawn. No code path relies on the process cwd.
- **`MISE_SAFE=1` choke point.** Every read funnels through `run_mise_json` →
  `run_mise_timed(..., true)` (`mise.rs:788`); writes go through the tracked runner and
  check trust first. Mutating commands cannot accidentally inherit the safe flag.
- **ADR-0007 affordances all exist.** Column resize with persistence
  (`Table resizeKey` on the Tools/Preview-tools/Preview-env/Env/Tasks/Settings tables),
  copy (Home raw JSON, Doctor upgrade notice, execution panel), and pre-action teaching:
  every install/use/uninstall/unuse/upgrade opens a `ConfirmDialog` that echoes the exact
  argv before dispatch.
- **Batch-operation bans held.** No `mise upgrade` without a tool, no `--bump`, no
  `uninstall --all`, no `plugins update` / `plugins ls --outdated` anywhere in `src/`.
- **Retired vocabulary is gone.** `作用域 / 上下文 / 项目 / 注册表` and `registry` as a
  section name: 0 hits across `en.json` + `zh-CN.json` (442 keys each, key sets identical).
  `registry` survives only inside `tools.commandHint`, where it is a literal command.
- **Version gate parsing.** `extract_date` handles the real `version` string
  (`"2026.10.15 macos-arm64 (2026-10-19)"`), the too-old payload uses the documented
  `key|param=value` wire format, and `HomePage.tsx:155-163` compares directionally.
  The `latest` field lagging behind a same-day release is mise's own 24h
  `minimum_release_age` cooldown, not an app defect.

## P1 — fix before GA

### P1-1 The upgrade chip advertises targets that `mise upgrade <tool>` cannot reach

- **Evidence (code):**
  - `mise.rs:857` — `mise_outdated` runs `outdated --json --bump`.
  - `lib.rs:505` — `tools_outdated` is a thin wrapper over it, so the frontend count and
    the Tools table both see the `--bump` payload.
  - `ToolsPage.tsx:369-372` filters with `hasUpgradeTarget` (`utils/versions.ts:99-101`:
    `latest !== current`), `ToolsPage.tsx:396` stores `latest`, `ToolsPage.tsx:517` renders
    `tools.upgradeChip` with it, and `ToolsPage.tsx:196-201` dispatches `["upgrade", tool]`
    *without* `--bump`.
  - `AddToolSection.tsx:276-297` repeats the same assumption and says so in a comment
    ("`mise outdated` reports the newest version within the config's range — exactly what
    `mise upgrade <tool>` (no `--bump`) reaches").
  - `api/miseTools.ts:118` parses `bump` into `MiseOutdatedItem.bump`… and no component
    ever reads it. `--bump` was added for a field the UI ignores, while changing the
    meaning of the field it does use.
- **Evidence (live, this repo + global config):**
  ```
  $ mise outdated --json          → { "rust": {requested:"latest", current:"stable", latest:"stable"} }
  $ mise outdated --json --bump   → additionally
        go    {requested:"1.27.1", current:"1.27.1", bump:"1.27.3", latest:"1.27.3"}
        maven {requested:"3.9.16", current:"3.9.16", bump:"3.10.0", latest:"3.10.0"}
  $ mise upgrade --dry-run go
    mise Newer versions are available but do not match the configured version ranges:
      go 1.27.1 → 1.27.3 (~/.config/mise/config.toml)
    Run `mise outdated --bump` to view all, or `mise upgrade --bump` to update the configuration and upgrade.
    exit=0
  ```
  Under `--bump`, `latest` is the **newest published version regardless of the request**;
  without it, `latest` is the **newest version inside the request**, i.e. exactly what
  `mise upgrade` can install.
- **Consequence:** for any tool pinned to an exact version — which is what `mise use` and
  this GUI's own Use button write (`mise use go@1.27.1` → `go = "1.27.1"`) — the Tools page
  shows `Update available · 1.27.3`, counts the tool in "N tools outdated", and offers an
  Upgrade button that **exits 0 and does nothing**. The chip does not clear afterwards
  (the next `outdated --bump` read reports it again). This is the app's primary upgrade
  affordance failing silently, and it contradicts the binding rule in
  `docs/design/ui-ux-rules.md` ("when `mise outdated` reports a newer **in-range** version…
  runs `mise upgrade <tool>` within the range the config file writes — never `--bump`").
- **Fix:** drop `--bump` from `mise.rs:857`. `latest` then means "in range" and every
  surface (chip, count, in-use header, `hasUpgradeTarget`) becomes correct without further
  edits. Delete the now-unused `bump` field from `types/tauri.ts:85` and
  `api/miseTools.ts:118`, and drop "`--bump`" from the three doc comments
  (`useToolsList.ts:4,113`, `api/miseTools.ts:108,124`). If "a newer major exists" is ever
  wanted as information, it belongs in a separate, non-actionable hint that names
  `mise upgrade --bump` — out of v1 scope per beta13 Q9.

### P1-2 The declared mise floor (`2025.1.0`) predates `ls-remote --json` by eleven months

- **Evidence:**
  - `mise.rs:25` — `pub const MIN_MISE_VERSION: &str = "2025.1.0"`.
  - `mise.rs:1041-1045` — the version picker runs `ls-remote --json <tool>`.
  - At tag `v2025.1.0`, `src/cli/ls_remote.rs` has exactly three options — `plugin`
    (positional), `--all`, `prefix`. **There is no `--json`.** The flag arrived in
    `feat(ls-remote): add --json flag with created_at timestamps (#7279)`,
    committed 2025-12-13, first released in **2025.12.5**.
  - Same tag, `src/cli/registry.rs` has no `--json` either (the app's text fallback
    covers that one, so it degrades), and `src/cli/tasks/ls.rs::display_json` emits only
    `{name, aliases, hide, description, source}` — no `run`, no `depends`, and `aliases`
    is a comma-joined **string**, not the array `parseTask` expects.
- **Consequence:** a user on mise `2025.1.0` … `2025.12.4` passes the gate, and then
  "Manage versions" fails with `unexpected argument '--json'` for every tool — the whole
  install/use path is dead while the app claims support. On those versions the Tasks page
  also lists tasks with an empty run (and saving one would rewrite it without a `run` key,
  because `mise tasks add` replaces the table).
- **Fix (pick one, in order of preference):**
  1. Raise `MIN_MISE_VERSION` to `2025.12.5` (the first release containing every flag the
     app needs), update `docs/agents/conventions.md` + README, and keep the too-old panel's
     upgrade path — that panel already exists and works.
  2. Or make the version list version-agnostic: `mise ls-remote <tool>` (plain text, one
     version per line) has existed forever; parse it as a fallback when `--json` fails, and
     treat `created_at` as optional (the Created column already renders "—").
  Option 1 is one constant; option 2 keeps `2025.1.0` honest but adds a second parser.
- **Same family, lower stakes:** on `2025.1.x`, `mise outdated --json` returns non-JSON when
  nothing is outdated (`fix: mise outdated --json does not return json if all tools are
  up-to-date`, #4493, 2025-02-22). So on the declared floor, an up-to-date machine shows a
  parse error instead of "all up to date". Fixed by either remedy above.

## P2 — cheap fixes / polish

### P2-1 Doctor's `errors` are structurally invisible

- **Evidence:** `mise doctor --json` calls `exit(1)` when it collected errors
  (`src/cli/doctor/mod.rs`, `if !self.errors.is_empty() { exit(1) }`). `run_mise_json`
  (`mise.rs:789-793`) checks the exit code **before** parsing and returns
  `COMMAND_FAILED`, so `mise_doctor` (`mise.rs:1468-1479`) always takes its
  `doctor_text_fallback` branch — on a broken install, i.e. exactly when a user opens
  Doctor — and runs `mise doctor` a second time to get tinted raw lines.
  `parseDoctorPayload` also never maps `errors`, and `DoctorPage.tsx` only reads
  `data.warnings`, so even a successfully parsed payload could not show them.
- **Consequence:** no data loss (the fallback prints the same lines), but the structured
  page — the v1 "presentation layer" deliverable — downgrades in the one case it exists
  for, and every failing doctor run costs two CLI invocations.
- **Fix:** give the doctor read its own parse path that accepts exit 1 when stdout parses
  as JSON, map `errors` into `DoctorPayload`, and render an Errors section above Warnings.

### P2-2 `plugins ls --urls` returns four columns; the app keeps two

- **Evidence:** `mise.rs:1567-1581` splits each line and keeps `parts[0]` as `name` and
  `parts[1]` as `source`. Upstream `plugins ls --urls` prints a `Row {plugin, url, ref,
  sha}` table (`#[tabled(rename_all = "PascalCase")]`), and `--help` says so:
  *"Show each plugin's Git URL, ref, and commit"*. The fixture
  `tests/fixtures/mise/plugins---ls---urls/stdout` is a hand-written two-column table, so
  the tests pin the wrong shape. (No header row is printed — `table::default_style(...,
  false)` suppresses it, same as `ls`/`registry` — so the parse does not fabricate a
  "Plugin" row.)
- **Consequence:** the ref and commit are dropped, so a plugin installed from a pinned ref
  is indistinguishable from one tracking `main`, and the Plugins page cannot show it.
  Worse, for a plugin with **no remote URL** the columns shift: `parts[1]` becomes the ref
  (`main`) and the UI renders `main` as the plugin's source URL — fabricated data, which
  `ui-ux-rules.md` (Data honesty) forbids.
- **Fix:** model `{name, url, ref, sha}`, split with `split_whitespace` and treat the
  *last two* tokens as ref/sha only when the line has ≥3 tokens (or skip columns by
  re-parsing with `splitn`); render Ref/Commit as their own columns, `—` when empty.
  Regenerate the fixture from real output.

### P2-3 The Overview env table has no source column, though the README and ADR-0003 promise one

- **Evidence:** `DirectoryPreview.tsx:312-333` renders exactly two columns (Name, Value)
  over `mise env --json`, which carries no provenance. README's Overview row says
  "Resolved tools and env, config files in precedence order with contents, `mise.lock` —
  each row with its source"; ADR-0003 names "config-hierarchy visualization showing which
  value comes from which file" as the GUI's differentiator over the CLI. Tools do carry a
  source badge; env does not.
- **Consequence:** the one page whose job is "where does this come from" answers that
  question for tools and config files but not for env vars, while the Env page next door
  answers it. The data is one flag away: `mise env --json-extended` (already used by
  `useEnvList`) returns `{value, source, tool}`.
- **Fix:** read `--json-extended` in `usePreviewEnv`, add a Source column rendering
  `source`/`tool` with the same `—` fallback, and reuse the Env page's source-badge
  component. Keep the two-column layout if a source cell would crowd it — but then correct
  the README sentence instead.

### P2-4 Two vocabulary drifts in copy

- **Evidence:**
  - `plugins.hint` (en/zh): *"the asdf-style or vfox-style **extensions** that teach mise
    how to install tools"* / *"asdf 风格或 vfox 风格**扩展**"*. `CONTEXT.md:17-19` defines
    Plugin and lists `_Avoid_: extension, addon`.
  - `tools.upgradeChip` (en): *"**Update available** · {{latest}}"* and
    `common.outdatedChecking` (en): *"Checking for **updates**…"*. `CONTEXT.md:80`:
    *"Unqualified 'update' means mise's own update (`mise self-update`); a Tool's newer
    version is an 'Upgrade'."* The zh side is already correct (`可升级`), so the two locales
    describe different concepts for the same chip.
- **Consequence:** the app teaches a term its own glossary retires, and EN/ZH disagree on
  the update/upgrade split that the glossary exists to protect.
- **Fix:** `plugins.hint` → "plugins that teach mise how to install tools" / "教 mise 如何
  安装工具的插件". EN chip → "Upgrade available · {{latest}}"; `common.outdatedChecking` →
  "Checking for upgrades…".

### P2-5 Sidebar grouping no longer matches `product-logic.md`

- **Evidence:** `PageShell.tsx:181-193` puts Home first in `NAV_ITEMS` and keeps only
  Doctor/Settings in `BOTTOM_ITEMS`. `docs/design/product-logic.md:48-49` specifies
  "Main group: Preview → Tools → Env → Tasks → Plugins" and "Bottom group: Home (mise
  status / guided install / self-update), Doctor, Settings". `HomePage.tsx`'s header
  comment still claims Home is *"deliberately not a nav item"*, matching the older
  brand-lockup design (#44/#49) rather than the shipped sidebar.
- **Consequence:** no functional break; the IA document that owns the sidebar is wrong, and
  the next contributor reading either file gets the opposite answer from the other.
- **Fix:** decide which one wins. If the shipped grouping is intended (Home as a landing
  page at the top is defensible), update `product-logic.md:48-49` and the `HomePage` comment;
  if the document is right, move Home into `BOTTOM_ITEMS`.

### P2-6 A task cannot be run with arguments

- **Evidence:** `TasksPage.tsx:124-126` — `miseRunTaskArgs(name)` returns `["run", name]`; there
  is no input anywhere on the page for additional words. mise tasks declare arguments via
  a usage spec (`mise run build -- --release`, `mise run deploy staging`), and `run --
  <args>` is part of the documented contract of `mise run`.
- **Consequence:** any task with required arguments is un-runnable from the GUI, and the
  page gives no hint why it failed (the task itself errors on the missing arg).
- **Fix (smallest honest version):** add an optional single-line "arguments" field next to
  Run, split it with the existing `splitShellWords` helper (`api/miseTools.ts`), and append
  `["--", ...tokens]` when non-empty. The confirm/echo path already prints whatever argv it
  is handed, so nothing else changes. A usage-spec-driven form is v2 work.

### P2-7 Two new mise fields the app ignores would close known gaps

- **Evidence (live 2026.10.15):**
  - `mise config ls --json` now returns `{path, tools, override}`; `mise.rs:1002-1017` reads
    only `path`/`tools`, so an `override = true` file (the one that wins over everything)
    is rendered identically to a normal one in the Preview precedence list.
  - `mise registry --json` returns `{short, backends, bins, description, aliases}`;
    `parseRegistryItem` (`api/miseTools.ts`) drops `bins`. For tools whose binary differs
    from the shorthand (`op` → `1password`), a user who knows the binary cannot find the
    tool — the exact failure mode the tiered search was built to avoid.
- **Consequence:** two cheap wins for fidelity; neither is a regression.
- **Fix:** add `override: boolean` to `ConfigFile` and a small "override" badge in
  `ConfigFileRow`; add `bins: string[]` to `RegistryItem` and include it in the haystack of
  the registry ranking (lowest tier).

## Not covered

1. Runtime verification of the chip → Upgrade round trip (static-only audit; the P1-1
   conclusion is from the CLI's own dry-run output, not from clicking the button).
2. Real mise builds older than 2026.10.15 — 2025.1.0 / 2025.12.5 behaviour is read from
   tagged sources, not executed.
3. Windows/Linux mise output differences (table padding, path separators in
   `plugins ls --urls`, `trust --show` line shape with drive letters).
4. Whether every page's command hint lists exactly its commands (doc-vs-UI sweep belongs to
   the screenshot/label pass; the six hints I read were consistent).
5. `mise.lock` v2 format changes — the app renders the file as text, so shape drift cannot
   break it, but no lockfile semantic checks were done.
