# 国际化（i18n）

> [English](../../../docs/agents/i18n.md)

MiseDeck 如何同时提供英语和简体中文，以及如何在不破坏这一承诺的前提下新增字符串。

> 「不拼接翻译字符串」的工程规则及其 `lint:i18n-concat` 守卫位于
> [`conventions.md` → i18n](conventions.md#i18n) —— 一条规则，一个家。

## 技术栈（已规定）

- **`react-i18next`**，在 `src/i18n/index.ts` 中初始化。
- 资源文件位于 `src/i18n/en.json` 和 `src/i18n/zh-CN.json`。
- 应用中每个键的类型化目录位于 `src/i18n/keys.ts`。
- 语言提供者位于 `src/i18n/useLanguage.tsx`，对外暴露
  `language` 和 `setLanguage`，将选择持久化在
  `localStorage("misedeck.language")`，变更时重新渲染消费者。
- 可复用的语言切换器位于 `src/components/LanguageSwitcher/`。

## 命名规范 —— 按区域分组的扁平 ID

键是点分路径，按功能区域分组。一级段对应应用中的一个目录（如果还没有对应目录，则对应一个逻辑分组）。在新增分组前先使用已有的——分组的权威、始终最新的清单是 `src/i18n/keys.ts`（目前为：`common`、`directory`、`sidebar`、`miseManagement`、`execution`、`failureNotice`、`tooltip`、`activation`、`nav`、`home`、`trust`，每个页面一个——`tools`、`preview`、`env`、`tasks`、`settings`、`doctor`、`plugins`——外加 `states`、`labels`、`errorBoundary`、`errors`、`languages`、`theme`、`about`）。

约定：

- 段内使用 **小驼峰**（`commandFailed`，而不是 `command_failed`）。
- `common.*` 中 **动词优先，名词在后**（例如 `search` 排在 `results`
  之前）；其他分组名词优先。
- **不要加位置或页面相关的前缀** —— 按区域分组而非按页面分组，
  这样在页面间迁移的标签可以保留其键。

## 如何新增一个字符串

三步，全部在同一次提交中完成：

1. **新增常量**到 `src/i18n/keys.ts` 中对应的分组
   （例如 `common.retry: "common.retry"`）。
2. **新增同样的路径**到 `src/i18n/en.json` 和
   `src/i18n/zh-CN.json` **两个文件**。相同的路径、相同的嵌套、
   相同的缩进。英文文案是语气上的权威；中文文案可以忠实翻译或
   本地化改写，但绝不能留空。
3. **使用该常量**作为调用点：
   ```tsx
   <button>{t(I18N_KEYS.common.retry)}</button>
   ```
   始终走 `I18N_KEYS` —— 绝不打字字符串字面量 —— 这样编译器可以
   在目录中捕获拼写错误。

然后运行守门脚本：

```bash
npm run lint:i18n
```

它必须以 0 退出码退出。如果不是，说明两个资源文件不同步
（见下面的"为什么每个键必须同时存在于两个文件"）。

## 为什么每个键必须同时存在于两个文件（在同一次提交中）

一个键存在于 `en.json` 但缺失于 `zh-CN.json` 意味着中文 UI 会静默
回退到英文文案。更糟的是，一个键存在于 `zh-CN.json` 但缺失于
`en.json` 意味着英文 fallback 本身也缺失，用户将看到原始的点分
路径。这两种都是 bug，我们希望它们在构建时被发现，而不是在用户
眼前被发现。

`scripts/check-i18n.ts` 遍历两棵 JSON 树，分别计算它们的叶子键
集合，如果不一致则以清晰的 diff 非零退出。该脚本被接入
`npm run lint:i18n` 和 `npm run ci` 聚合命令。**CI 红意味着有键
只落在了一个文件里。** 修复方法是补齐缺失的翻译（或删除未使用
的键），不是禁用这个检查。

## 语言如何被选择

检测链路按优先级顺序：

1. **`localStorage("misedeck.language")`** —— 用户在
   `<LanguageSwitcher>` 中显式选择语言时设置。跨重启保留；
   覆盖下面所有项。
2. **浏览器语言**（`navigator.language`）—— 操作系统偏好，
   首次运行由 `i18next-browser-languagedetector` 解析。
   中文区域浏览器以 `zh-CN` 启动；其他以 `en` 启动。
3. **Fallback** —— `src/i18n/index.ts` 中的 `fallbackLng: "en"`。
   上述都没有匹配时，UI 显示英文。

提供者会在每次 `languageChanged` 事件上重新渲染，因此切换切换器
会更新所有可见文案而无需重新加载页面。

## 错误码存放在哪里

`docs/agents/conventions.md` 钉住了一组固定的 `AppError.code` 取值：

```
MISE_NOT_FOUND  MISE_TOO_OLD  COMMAND_FAILED  PARSE_FAILED  TIMEOUT  TERMINAL_NOT_FOUND
```

键形的 `AppError.message` 负载通过 `errors.*` 分组解析。Rust 侧可能
发出的键有：

- `errors.miseNotFound`（MISE_NOT_FOUND）
- `errors.miseTooOld`（MISE_TOO_OLD；携带 `{{found}}` / `{{minimum}}`）
- `errors.terminalNotFound`（TERMINAL_NOT_FOUND）
- `errors.timeout`（TIMEOUT）
- `errors.captureCap`（PARSE_FAILED；携带 `{{limit}}`——以 MiB 表示的捕获上限，
  在 Rust 侧就换算成人类可读的形态，读者不必自己把字节数换算一遍）
- `errors.parseFailed`（PARSE_FAILED；携带 `{{cmd}}` / `{{shape}}`——运行过的命令，
  以及 MiseDeck 期望的负载形状。两侧都会发出它：前端的形状校验
  （`api/miseTools.ts`、`api/mise.ts`）与 Rust 边界
  （`src-tauri/src/mise.rs`）。整类失败共用一条消息，因此 zh-CN 界面永远不会
  渲染 MiseDeck 自己撰写的英文细节）
- `errors.commandFailed`（COMMAND_FAILED；携带 `{{cmd}}` / `{{code}}`——运行过的
  命令及其退出码。Rust 边界对每一次非零退出都会发出它：`mise trust --show`、
  `mise doctor`、`mise registry`、`mise plugins ls`、`mise tasks edit --path`、
  `mise self-update`，以及通用的运行边界）
- `errors.installFailed`（COMMAND_FAILED；携带 `{{code}}`——官方 mise 安装脚本的
  退出码）
- `errors.spawnFailed`（COMMAND_FAILED；携带 `{{task}}` / `{{reason}}`——该操作与
  操作系统错误。操作系统给出的文本是数据，不是文案）
- `errors.waitFailed`（COMMAND_FAILED；携带 `{{task}}` / `{{reason}}`——该操作与
  操作系统错误）
- `errors.backgroundTaskFailed`（COMMAND_FAILED；携带 `{{task}}`——后台任务失败
  的那个操作）
- `errors.cancelled`（COMMAND_FAILED；携带 `{{task}}`——被用户取消的那个操作。
  它同时是运行器的取消签名：`useExecution.ts` 会精确匹配这条消息，把与取消
  竞速的拒绝判定为“已取消”而不是“失败”（issue #301））
- `errors.emptyArg`（COMMAND_FAILED；携带 `{{arg}}`——为空的参数）
- `errors.invalidArg`（COMMAND_FAILED；携带 `{{arg}}` / `{{value}}`——被拒绝的
  参数及其取值）
- `errors.notADirectory`（COMMAND_FAILED；携带 `{{path}}`——不是目录的那个路径）
- `errors.readFailed`（COMMAND_FAILED；携带 `{{path}}` / `{{reason}}`——该文件与
  操作系统错误）
- `errors.homeNotFound`（COMMAND_FAILED——无法解析主目录）
- `errors.unparsableOutput`（COMMAND_FAILED；携带 `{{cmd}}`——MiseDeck 无法读取其
  输出的那个命令。原始输出原样留在 `stderr` 字段里）
- `errors.terminalLaunchFailed` / `errors.terminalLaunchExited` /
  `errors.terminalLaunchTimeout`（COMMAND_FAILED；携带 `{{platform}}` /
  `{{app}}` / `{{path}}` / `{{command}}`，以及 `{{reason}}`、`{{code}}` 或
  `{{seconds}}`——被启动的终端、为哪个目录启动，以及尝试执行的完整 argv）
- `errors.linkRejected`（COMMAND_FAILED；携带 `{{reason}}`——链接在到达浏览器之前
  被拒绝的原因）
- `errors.browserRefused`（COMMAND_FAILED；携带 `{{reason}}`——opener 自身的错误）
- `errors.updateFeedInvalid`（COMMAND_FAILED；携带 `{{reason}}`——发行说明不是
  发行说明的原因）
- `errors.updateCurlFailed`（COMMAND_FAILED；携带 `{{reason}}`——curl 报出的
  操作系统错误）
- `errors.updateFeedTooLarge`（COMMAND_FAILED；携带 `{{limit}}`——发行说明超过的
  字节上限）
- `errors.updateRequestFailed`（COMMAND_FAILED——发行说明请求未成功）
- `errors.shellRcUnreadable`（COMMAND_FAILED；携带 `{{reason}}`——读取 shell 的
  rc 文件时的操作系统错误）
- `errors.windowChromeFailed`（COMMAND_FAILED；携带 `{{reason}}`——给窗口套用主题
  时的操作系统错误）

前端自己发出的键有两个 —— `errors.ipcFailed`（COMMAND_FAILED；携带
`{{detail}}`——运行时自身的拒绝文本）与 `errors.unexpectedIpcResponse`
（COMMAND_FAILED——IPC 边界返回的东西并不是一次运行结果）。两者都是：MiseDeck
自己的措辞是目录里的句子，运行时的文本则是它携带的数据。

`errors.parseFailed` 的 `shape` 参数是一个与语言无关的记号，而不是一句散文：
它指向目录中 `errors.shape.*` 下的某个叶子（`array`、`configFilesResult`、
`documented`、`objectBySetting`、`objectByTool`、`objectByVariable`、
`report`、`rowsWithPath`、`validJson`、`versionDate`、`versionString`），而目录在
两种语言下都保存着该记号对应的措辞。`resolveAppErrorMessage` 会在翻译消息之前
先查出这个措辞，因此 Rust 侧发出记号时无需知道读者使用的语言。新增一种形状
意味着在两个资源文件中都加上该记号 —— 若 Rust 侧也会发出它，还要加到
`src-tauri/src/mise.rs` 的 `parse_shape` 模块里。`documented` 是解析器在
“解析失败没有指明形状”时的兜底：句子依然完整，并且仍然点明运行过的命令。

命令失败这一整类用的是同样的约定：凡是“指明一种类别”而非承载数据的参数，
都携带一个与语言无关的记号。`{{task}}` 指向 `errors.task.*` 下的某个叶子
（`cwd`、`install`、`mise`、`other`、`selfUpdate`、`trust`），`{{arg}}` 指向
`errors.arg.*` 下的某个叶子（`command`、`cwd`、`flag`、`other`、`task`、
`theme`、`tool`），`{{reason}}` 指向 `errors.linkReason.*` 下的某个叶子
（`credentials`、`empty`、`host`、`other`、`scheme`、`tooLong`、
`whitespace`）或 `errors.feedReason.*` 下的某个叶子（`noEntry`、`notAtom`、
`other`）。每一组的 `other` 叶子是解析器在“失败没有指明类别”时的兜底。Rust 侧
发出的是同一批记号 —— `src-tauri/src/mise.rs` 里的 `token` 模块 —— 前端则在
`MESSAGE_TOKEN`（`misedeck/src/utils/appError.ts`）里与之对应。

参数值里若含有 `|` 分隔符，会在上线时被百分号编码（`|` → `%7C`，
`%` → `%25`），因此路径、argv 或运行时消息都不会把消息拆成 bogus 参数。
前端在 `parseAppErrorMessage` 里解码。

`errors.unknown` 是解析器对“目录里不存在的键形 message”的兜底 ——
原始键永远不会被渲染出来。

UI 中每一个展示 `err.message` 的位置都通过
`resolveAppErrorMessage`（`misedeck/src/utils/appError.ts`）解析，
它负责拆解 `key|param=value|…` 线格式；对不是键形的消息则原样透传。
解析失败是键形的（issue #310），命令失败同样是键形的（issue #311），
因此两者都和其他消息一样经由目录解析；早于这些键的细节仍会原样渲染。
拥有专属页面状态视图的 code 保持现状：HomePage 的 too-old
门禁渲染 `states.tooOld.*`，只从 `message` 里解析参数（通过共享的
`parseAppErrorMessage`）。

**mise 自己的 stderr 永远不加键。** 它是 CLI 的输出 —— 是数据，不是文案 ——
并且原样留在错误的 `stderr` 字段里（若该错误没有别的字段可放，就作为参数
携带，而目录不会翻译它）。只有 MiseDeck 自己的措辞才加键。

解析器在 `KNOWN_MESSAGE_KEYS` 集合中引用这些键，正是因为动态解析对
静态 `t()` 调用点扫描不可见 —— 不要把它们当作“死键”删掉。

UI 对 `code` 做模式匹配（见 `conventions.md`）来决定人类可读文案。
发明新错误码是有意识的 API 变更 —— 提一个 issue、更新本文档、
在两个资源文件中新增键，并在同一次改动中扩展
`misedeck/src/types/tauri.ts` 和 `misedeck/src-tauri/src/mise.rs`。

## 新增一种语言

`src/i18n/useLanguage.tsx` 中的 `SUPPORTED_LANGUAGES` 是一个
`const` 元组 —— 若要新增第三种语言：

1. 把 BCP-47 代码（例如 `"ja"`）追加到该元组，并追加到
   `src/i18n/index.ts` 中的 `supportedLngs`。
2. 在现有两个文件旁新增一个 `src/i18n/<code>.json`。
3. 更新 `I18N_KEYS.languages` 的展示标签，并把新选项加入
   `useLanguage.tsx` 中的 `LANGUAGE_LABELS`。
4. 把每个已有键翻译进新文件（`lint:i18n` 脚本会在达到对等之前
   拒绝通过）。
